# PILOT.md

What a plane can and cannot do in this repo. The node quotes this page whole into the planner, worker and reviewer
briefs, so it stays short. `CLAUDE.md` holds the architecture and conventions; this page holds only what a flight
needs to plan, build, check and land.

## What a plane can and cannot do

- A plane is a git worktree at `<repo>/.claude/worktrees/<code>` on `flight/<code>`. Work and commit only there. Do not
  push, open a PR or merge; the controller lands the flight. Leave nothing uncommitted, and put scratch output
  outside the plane.
- Sibling clones are not yours, and a plane cannot see them. `UseLocalFontsLib`, `UseLocalShapingLib` and
  `UseLocalLalrCc` look for `Fonts.Lib` and `LALR.CC` at `..\..\..` from each project, which from a plane is
  `.claude/worktrees/`, where none lives. So a plane restores the pinned `SharpAstro.Fonts` and `SharpAstro.LALR.CC`
  packages, as CI does. A change that needs a sibling to change is its own flight in that repo: name it and leave it.
- DIR.Lib is the foundation of `Console.Lib`, `SdlVulkan.Renderer`, `WebGl.Renderer`, `tianwen` and `pilot`. A plane
  cannot build them, so a change's effect on a consumer is named in the leg's report, not checked.
- No display, GPU or window is reachable from a plane, and none is needed: rendering is checked through
  `RgbaImageRenderer` and the baseline tests.
- Never wait with a job that sleeps or polls: use `pilot leg wait --for-file <path>` and end the turn. Long builds
  and test runs go through `pilot run -- <command>`. The machine is shared, so a job may wait its turn first.

## Build and check

Always `-c Release`, as CI does. Run from the repo root.

```bash
dotnet build DIR.Lib.sln -c Release
dotnet test src/DIR.Lib.Tests -c Release --no-build
dotnet test src/DIR.Lib.Shaping.Tests -c Release --no-build
```

- Tests are xunit.v3 with Shouldly on Microsoft.Testing.Platform, not VSTest: `--logger` and `--blame-*` fail the run.
  `--filter` keeps its VSTest syntax. A narrower check filters with `--filter "FullyQualifiedName~<Name>"`.
- The debug inspector (`DIR.Lib.Diagnostics`) and its tests are `#if DEBUG`, so a Release run compiles them out. A leg
  that touches the inspector checks with `-c Debug` as well. The LAN multicast test stays skipped: it needs
  `DIR_LIB_INSPECTOR_LAN_TESTS=1` and makes Windows Firewall prompt.
- A visual test that fails against its PNG in `Baselines/` is investigated, never regenerated as the first answer.
  A leg that changes rendering on purpose regenerates only the baselines it means to change
  (`DIR_LIB_UPDATE_BASELINES=1` with a filter) and names each one in its report.
- Each fixture font in `src/DIR.Lib.Tests/Fonts/` has one purpose (Merida is chess-only); read what a fixture is for
  before a new test uses it.
- `src/DIR.Lib/EmojiPresentation.Data.g.cs` is generated by `tools/gen-emoji-presentation`; never hand-edit it.

## Compatibility and release

- Consumers compile against the published package, so a binary break is a real break even when every caller still
  compiles. An optional parameter added to a record's primary constructor is one: prefer an init-only property, or add
  an explicit old-arity constructor and `Deconstruct`. `InputEventCompatibilityTests` pins this.
- AOT compatibility is required: no reflection-based patterns.
- A flight that ships a release bumps `VersionMajorMinor` in `src/Directory.Build.props` (additive is a minor, a break
  is a major) and adds its `## Major.Minor` entry to `CHANGELOG.md` in the same commit. Nothing derived from that
  number is hand-edited. Package versions live in `src/Directory.Packages.props`, never in a `.csproj`.

## How a flight merges

- main has no merge queue, but its ruleset requires **linear history**, so a PR lands by squash or rebase, never as a
  merge commit. Take main by a merge (`git fetch origin`, `git merge origin/main`), never a rebase, and never push with
  `--force`. A merge that resolved a conflict cannot be rebased onto main; say so in the leg's report, so the PR
  lands squashed.
- Keep a flight's commits few and each one whole.

## Writing

No em-dashes, and no `--` in their place: a full stop, a comma, a semicolon or parentheses. This holds for prose,
comments and commit messages.
